## 2026-10-18 · 第 8 段：审计通道自身的坐标 bug（**我自己的错，重要教训**）

| 项 | 内容 |
|---|---|
| 现象 | `--hud-ui-audit` 报 `176 击 / 0 灰块 / PASS`，但技能窗的页签几乎都不响应：只有 `Holy` 一个页签的点击进了 `SelectSchool`（`Fire` 是开窗时自动选的） |
| 中途错误结论 | 我先判定"页签与技能列表在 x=15 处重叠、点击被列表截走"，并据此**废弃**了"自绘三个额外文字页签"的方案、改成把 14 个技能塞进「剑(Physical)」页签。**这个结论是错的。** |
| 真根因 | 走查自己算点击坐标时用了 `GetViewport().GetCanvasTransform()` —— 那是**世界相机**的变换，对 CanvasLayer 上的 UI 控件根本不适用，鼠标实际没落在控件上。用 `GuiGetHoveredControl()` 探测发现：几乎每次点击位置都是"无控件"（`receiver=(null)`）。也就是说 `0 灰块 PASS` 只证明了"画得出来"，**没证明"点得到"** |
| 处置 | `HudUiAimAsync`：三个候选坐标（`Control.GetScreenTransform()` / `GetGlobalTransform()` / 旧 canvas 法）逐个试，每个都用**悬停控件自校验**（鼠标下方必须是目标控件或其子节点）→ 命中即用；全不命中则如实标 `unreachable` 且**不点**。`--hud-ui-audit` 结果行新增 `receiver=` 字段记录"实际谁收到了事件" |
| 验证 | `screen_transform` 候选下 **74/74 全部命中**（`hit=False` 为 0），魔法窗每个控件都落到各自不同的控件；`SelectSchool` 收到**全部 8 个经典页签** |
| 后续更正 | 既然页签本来就能点，技能窗回到**语义清晰**的方案：8 个经典页签原样不动，另外追加三个**中文专属页签**（主动/开关/被动），并把位置从"经典页签正下方"（实测有两个被同区域控件盖住 → `unreachable:none_hit`）挪到**技能列表下沿之外的空白横排**（y=491、x<120 一带：列表到 (390,488)、滚动条到 y=492） |
| 实机结果 | 三个新页签各自生效：`SelectSchool Passive` + `category=Passive count=2`、`SelectSchool Toggle` + `category=Toggle count=3`、`SelectSchool Active` + `category=Active count=9 page=1/2` —— 正好 **2+3+9 = 14** 个原先没有任何入口的技能。全量 `clicks=183 gray_blocks=0 PASS`；125 次命中、12 个不可达控件如实标注 `unreachable`（如 `consignment` 分类列表里滚动区外的项） |

**教训（写进纪律）**：验证工具的坐标空间必须**自校验**（点之前先确认"鼠标下方就是目标控件"），
否则"控件被点到"只是审计自己的假设；`0 灰块` 这类指标只能证明绘制，不能证明可达。

### 第 9 段·结论修正（避免夸大）

组 A（技能显示名）落地后实测客户端本地化链路：`GodotClient/Scripts/LocalizedName.cs:97` 是
`Lookup(_magics, info?.Name, info?.Name)` —— 中文名按**英文 `Name` 查表**，而
`GodotClient/Translations/db_names.json` 里**两种拼写都被收录**（`LightningBeam` 与 `Lightning Beam`
都映射到「疾光电影」，其余同）。也就是说：**改名前后玩家看到的都是中文**，这条修复**不是**修玩家可见的坏显示，
而是**数据规范**——库内英文名是键，`LightningBeam` 这种枚举标识形态与其余 45+ 条技能、以及旧库都不一致，
会误导其它消费方（服务端日志、`@` 命令按名查找、外部工具）。
附带收获：我机械拆分出的 `Thunder Strike` 在翻译表里**本来就有条目**（「怒神霹雳」），
反证那条命名约定（CamelCase → 空格分词）是对的。

### 第 9 段·顺带得到的两个结论

1. **悬空引用全面扫描 = 0**：80 张表、2.6 万+ 条引用，以导出 `meta.json` 的 `type=ref/reflist` 为唯一判据逐字段核对，
   引用名与目标行身份全部一致；独立复核 4 项（重新导出 81/81 相同、无未登记引用字段、Index 唯一性、哨兵值边界）全过。
   注意方法学：MirDB **加载时会把悬空引用置 null 并被导出跳过**，所以"导出里 0 悬空"等价于"库内可达引用全部自洽"，
   不等于"原始 .db 里没有残留的坏索引"。
2. **不恢复清单（口径，已按纪律维持）**：8 张 0 刷怪地图的 32 行旧刷怪。补充实测（更正第 9 段早先的判断）：这 8 张图是打怪图（邪恶之地①②、深度雪原、绝情塔 1/2 层、绝情宫殿、玛法·四象），但现库里**区域 0、出入口 0、刷怪 0**（绝情塔两层尚存 6–7 区域）→ 被整块清空；因此连那 3 行"怪物仍在"的刷怪也无法单独恢复（其 MapRegion 同样被删）→ 恢复成本 = 区域 + 怪物 + 掉落；
   199 只已删怪物 / 582 件已删物品（实测当前库对其零引用）；3 条 `Item == null` 的奖励行（望海楼之约战士/法师、刺杀剑术觉醒）
   —— 旧库无对应任务、意图不可考，故只保留已有的空 Item 守卫（`c26b7bd8`），不发明奖励物。

## 2026-10-18 · 第 13 段：走查报的"不可达控件"确实是真缺陷（已修两处）

| 项 | 内容 |
|---|---|
| 诊断手段 | 给走查加两样东西：`--hud-ui-audit-only a,b`（只跑指定窗口，诊断从 10 分钟降到 1 分钟）；瞄准失败时打印**每个候选坐标下实际悬停到的控件** |
