## 1. 方法与判据

### 1.1 独立实现（不与生产工具共用逻辑）

`.map` 解析完全自写（`MapFile` 类），未 import `Mir3-Research/Tools/mapedit`、`mapio` 或任何生产解析函数：

```
0..21   22 字节头
22..23  int16 Width（小端）
24..25  int16 Height（小端）
26..27  跳过
28..    地面层 (Width/2)*(Height/2)*3 字节（1 byte backFile + 2 bytes backImage）
之后    全分辨率格区，14 字节/格，列优先：格索引 = x*Height + y
格内偏移：0 flag / 1 middleAnimFrame / 2 frontAnimFrame / 3 frontFile / 4 middleFile /
          5-6 middleImage(+1) / 7-8 frontImage(+1) / 9-11 跳过 / 12 light / 13 跳过
```

通行判据：**`flag & 0x03 == 0x03` 为可站**。该约定由三处独立代码交叉确认：
`BotRunner/BotMap.cs:41`（`(flag & 0x03) != 0x03 → blocked`）、
`ServerLibrary/Models/Map.cs:75-88`（`offSet = 28 + Width*Height/4*3`，`(flag&2)==2 && (flag&1)==1` 才进 `ValidCells`）、
`GodotClient/Formats/MapReader.cs:47-80`。本脚本不调用它们，只按其约定实现。

### 1.2 解析正确性的三重验证

1. **尺寸恒等式**：627 个文件中，588 个满足 `len == 28 + (W/2)*(H/2)*3 + W*H*14`，
   39 个满足 `... + W*H*13`，**0 个两者都不满足**。头部宽度/高度由算术唯一反解出偏移 28，独立于任何代码约定。
2. **空间连通性检验**（用于判定 stride 13 还是 14）：正确对齐时"可站格的四邻域也可站"（coherence）应显著偏高。
   控制组 `D202.map` 在 stride14 下 coherence=0.702、stride13 下 0.026；`3.map` 为 0.934 / 0.594。
   39 个异常文件则在 stride13 下 0.41–0.73、stride14 下 0.00–0.30 → 这 39 个文件确实按 **13 字节/格**记录。
3. **同一文件多副本一致性**：39 个异常文件在 `mir2ei/Map`、`Debug/Client.before-mir2ei-20260925/Map`、
   `Development/Debug/ServerCore/Map` 三处 MD5 完全相同（例：`D601.map` = `26f105f6…`），
   且与 82 上的 `Debug/ServerCore/Map/D601.map` 相同 → 是发行数据，不是本地拷贝损坏。

### 1.3 端点坐标的来源与其精度

`MapRegion.PointRegion` 在库导出中只有 `{PointCount, CenterX, CenterY}`。其定义来自
`Mir3-Research/Tools/SystemDbProbe/Program.cs:1310-1322`：`CenterX/Y` = 该区域所有点 X/Y 之和
按点数整除（截断）→ **质心**。因此：

* `PointCount == 1` 时质心即该区域**唯一**格，判定是精确的（本轮 10 条硬问题全部属于此类）；
* `PointCount > 1` 时中心只是代表点：中心不可站但 8 邻域仍有可站格 → 只记 `warn`（该区域其他点可能可用），
  中心不可站且 8 邻域全不可站 → 记硬问题。
* 库导出未含 `BitRegion`（位图区域）；`MapRegion.BitRegion` 存在时服务端运行时优先用它
  （`MapRegion.cs:164-186`）。本轮 4621 个区域中 4620 个带 `PointRegion` 且有 1 个为 `None`，
  该 1 个不是任何连接端点，不影响连接结论。

### 1.4 服务端后果（症状到代码的对应）

`ServerLibrary/Models/Map.cs:547-730`：

* **落点格不可站** → `map.GetCell(destination) == null` → `continue`（随机取点重试，最多 5 次）。
  单点区域每次都取同一格 → **传送静默不生效（踩门无反应）**。
* **源格不可站** → `SEnvir.CreateMovements`（`ServerLibrary/Envir/SEnvir.cs:807-892`）不会把该 movement

  （`endpoints_pocket = 0`），即当前没有"传过去困死"的连接。

### 3.1 【确认缺陷（代码层）】39 张地图是 13 字节/格记录，Zircon 按 14 字节/格读

文件：`0_0011/0_002/0_0021/0_0031/0_0032/0_0033`、`D601–D619`（16 张）、`d608–d611`、
`kt0002–kt0018`（含 `kt00161`、`kt00181`，共 21 张）。

* 尺寸恒等式：`len == 28 + (W/2)*(H/2)*3 + W*H*13` 精确成立（例 `D601.map` 250×250：859403 =
  28+46875+62500×13；14 字节/格需要 921903 字节，文件少 62500 字节 = 每格少 1 字节）。
  14 字节/格对这些文件**在算术上不可能成立**（所需字节数大于文件长度）。
* 对齐证据：stride 13 下 flag 字节空间连通性 0.41–0.73（与正常图同量级），stride 14 下 0.00–0.30。
* 39 张**全部登记在 `MapInfo`**（因此可以被 `@move`/配置进入）；其中 `D601`(2 条)、`D602`(4 条) 还有刷怪区域。
  它们不是任何 `MovementInfo` 的端点，也没有 NPC。
* 后果（代码层确证，未实机验证）：
  * 客户端：`MirMap` 构造按 14 字节/格顺序读到文件尾 → `EndOfStreamException`；
    `MapView.LoadMap`（`GodotClient/Scripts/MapView.cs:83-94`）捕获后打印
    `[MapView] 地图加载失败 <stem>` 并放弃加载 → 地形不显示。
  * 服务端：`Map.Load()`（`ServerLibrary/Models/Map.cs:66-89`）按 `fileBytes[offSet + i*14]` 取值，
    最大下标 921889 > 文件长度 859403 → `IndexOutOfRangeException`。该异常从
    `SEnvir.GetMap → FinaliseMapLoad → map.Load()`（`SEnvir.cs:4308-4348`）抛出，沿途**无 try/catch**；
    而 `Maps[info]` 在 `FinaliseMapLoad` 之前就已赋值，所以之后再次进入会拿到一个
    `Cells` 半初始化的 Map（大量 null 格）→ 后续 `NullReferenceException` 而非直接崩溃。
    `Config.LazyLoadMaps` 默认 `true`（`ServerLibrary/Envir/Config.cs:33`），地图按需加载，
    所以启动阶段不会踩到——**只有真的进入这 39 张图才会爆**。
* 建议（见 §4）：优先给这 39 张图补齐 14 字节/格版本（或给 `MirMap`/`Map.Load` 加 13 字节/格分支），
  并先在一张图上做游戏内验证。

### 4.2 区域名称里的 `@(x,y)` 交叉（可作修复候选坐标，但要用对语义）

新库区域名大量形如 `<源图> -> <目标图> @(x,y)` / `… @(x,y) 落点`：

| 组 | 区域数 | 质心 == 名称坐标 | 偏差 >10 格 | 名称坐标在同图可站 |
|---|---:|---:|---:|---|
| 源侧（名称不含"落点"） | 1558 | 1521 | 19 | 1527 True / 23 False / 8 越界 |
| 落点侧（名称含"落点"） | 1558 | 0 | 1536 | —（该坐标通常指**源地图**的门口，不能用于目标图判定） |

→ 对**源侧**区域，名称里的 `@(x,y)` 基本就是该区域的格，可当修复候选；对**落点侧**区域不行。
11 条可疑连接的建议候选格 = §4.1 表中"最近可站格"列（与名称坐标一致时优先用名称坐标）。

### 4.3 双向配对与"只进不出/只出不进"

* 区域级完全反向（源区域/目标区域互换）**0 条**——这是设计使然：对向的两扇门使用不同的 Region 对象
  （`X / Door` ↔ `Y / Landing`），所以"区域级反向缺失"不能当缺陷判据。
* 地图级有向边 877 条，其中 747 条存在反向边，**130 条单向**（多为 `D4xx → D4xx_001` 这类定点跳转）。
* **只进不出（有入边、无出边）30 张**：其中 16 张是 `D401_001`–`D452_001` 的同构模式（入边均 5 条，明显同一批生成），
  另有 14 张：`02_003`、`1_011`、`D0002_004`、`D024`、`D10162`、`D1116`、`D2204`、`D3704`、`D90222`、`d1506`、`d2005`、`d2106`、`d515`、`d9093`。

## 8. 不确定项与未覆盖

1. **`PointRegion` 质心语义**未能用二进制直接解码 `System.db` 复核（硬性约束：脚本不读 System.db）。
   依据是导出工具源码（`SystemDbProbe/Program.cs:1310-1322`）+ `out/meta.json` 可确认导出工具与字段命名。
   若该行代码与实际导出脚本不一致，§4 的坐标需重算（但 `PointCount==1` 的结论不受影响）。
2. **13 字节/格**是"格式变体"还是"损坏"。判定依据是尺寸恒等式 + 空间连通性 + 多副本 MD5，
   三者都指向变体；但本轮**没有实机验证**（未启动客户端/服务端）——建议进一张图确认现象后再决定修哪一侧。
3. **服务端异常的实际表现**（`IndexOutOfRangeException` vs 日志吞掉）只能由代码路径推断；
   `FinaliseMapLoad` 无 try/catch，但最外层 packet 处理有 try/catch（`LibraryCore/Network/BaseConnection.cs:418-445`，82 的
   `Errors.txt` 里是这类堆栈），所以可能是"报错+进图失败"而不是崩溃。**待实机确认**。
4. **落点侧区域名称坐标的语义**（属于源地图 vs 目标地图）没有权威文档，本轮按"不能用于目标图判定"处理。
5. 本轮**未覆盖**：`SafeZoneInfo`/`GuardInfo` 坐标可站性、NPC 登记格可站性（只统计了每图 NPC 数）、
   `RespawnInfo` 区域可站性、`InstanceInfo`（该表为空）、网站 `maps[]` 的 `env`/等级字段与 `MapInfo` 等级的逐项比对。
6. 与连接无关的地图使用缺口（如 `z010`/`z014`、`E003/E004/E007`、`ID1_*`/`ID2_*` 等 83 张仅在磁盘存在）
   只做了"是否登记在 MapInfo"的判定，没有逐个确认玩法用途。
