## 0. 为什么重测

`NPCDialog.cs` 里关于几何的注释是**多轮推测的叠加**，彼此矛盾：

```csharp
// N5 证据 npc-dialog-family-evidence.json：type-1 文本的换行门是 0x95 = 149px，
```

这段注释自己就承认了「自推导值」「越出可见面板」——但常量一直没改。

本轮直接量素材，不再推测。

## 2. 关键推论

### 2.1 窗口逻辑尺寸 552×176 与素材 512×256 不矛盾

- 反汇编证据 `exe_trace.npc_window` 写 `frame 1100 552x176` → 这是**窗口对象逻辑尺寸**
- 素材实测 F1100 = **512×256**，alpha 可见区 **384×138**

两者是不同坐标系：窗口逻辑框 552×176，背景帧画进来后**只有 384×138 的木框区域可见**，
其余是透明。代码 `Size = 552×176` + `_headerBackground.Location = (-64,-59)`（把 bbox 原点对到窗口 0,0）
在数学上**是自洽的** → **不改**。

### 2.2 背景锚点 (-64,-59) 符合全仓约定，**不改**

`BeltDialog.cs:125-129` 的注释说明了统一约定：

```csharp
// 与其余 10 个 legacy 窗相同的约定：把该帧 alpha 可见区原点对齐到窗口 (0,0)。
// 素材实测 F850 的 alpha bbox 原点 (118,94)，故取 -(118,94)。
// 原值 (-7,44) 用的是 WIL header offset（-headerOffset），不是 bbox 原点 ——
```

**全仓 11 个 legacy 窗都用 bbox 对齐**，NPCDialog 已按此统一。改它反而会破坏一致性。

### 2.3 行距 21/14 有反汇编证据，**不改**

```
原版 0x440AA0 扫描器：
  mode(this+0x582)=1    ⇔ 文本含 {NPCIMG
  overflow(this+0x58C)=1 ⇔ (raw_segment_count − 6) > 16
  line spacing(this+0x594) = 14 仅当 mode==1 && overflow==1，否则 21
```

`default_line_spacing_px = 21` 有出处。反汇编里另一处 `y = line*0x14`(=20) 属于**不同 type 分支**，
不能拿来覆盖 type-1 的 21。

### 2.4 ⚠️ 两列 x 坐标存在未解矛盾（本轮唯一未搞定的问题）

反汇编原文（`npc-dialog-family-evidence.json::cell_analysis.type1_0x43F4E7`）：

```
text: 0x45E0C0 measure line [ebx+4];
x = 0x131 - 0x6B when line >= 7 (2-column);
y = line*0x14; wrap at 0x95 width
```

| 读法 | 第一列 x | 第二列 x | 是否自洽 |
|---|---|---|---|
| **A（当前代码）** | 150 | 305 (`0x131`) | ❌ 305+149=454 越出可见宽 384 |
| **B（字面减法）** | 150 | 198 (`0x131-0x6B`) | ❌ 150+149=299 > 198，两列重叠 |
| **C（反推第一列）** | 49 | 198 | ⚠️ 49..198 / 198..347 都在 384 内，但**与头像冲突**（头像右缘 161） |
| **D（x 是条件赋值）** | 默认值（证据未给） | 198 | ❓ 缺第一列默认值 |

**本轮尝试**：按读法 C 改成 49/198，编译 + 跑 `--legacy-npc-selftest`（PASS），
但看截图发现**头像把正文左半边全遮住了**（头像可见区 64..161，第一列从 49 开始必然被压）。
→ 已**回滚到原值 150/305**，不引入未验证的改动。

**结论**：`0x6B = 107` 的确切语义仍未确定，**需要原版客户端截图做像素比对**才能定论。

### 2.5 头像与文字的重叠是真实存在的

- 头像绘制点 `LegacyNpcFacePosition = (40,30)`，有反汇编硬编码常量支撑
  （`0x440059: push 0x1e(30) / push 0x28(40)`）
- NPCface.wil 帧 offset = `(-24,-16)`，按 WIL 语义「帧内(0,0)画在 绘制点+(24,16)」
  → 可见区落在窗口 **(64,46)-(161,168)**
- 正文第一列 x=150 → **与头像右缘 161 重叠 11px**

这 11px 重叠可能就是实机截图里「每行开头几个字被盖住」的原因。
但**不能简单改头像位置**——(40,30) 有反汇编常量支撑，
需要确认引擎绘制时 **是否已自动处理 offset**（若已处理，则我的推算整体偏移 24,-16，结论不成立）。

### 6.3 与当前实现的差异（这就是要修的）

| 维度 | 原版（截图） | 当前实现 | 判定 |
|---|---|---|---|
| **窗口高度** | **动态**，随内容增长（约 355px） | 固定 `Size=(552,176)` | **根本差异** |
| **窗口结构** | 顶/中/底三段，中段可拉伸 | 单张 F1100 铺满 | 不符 |
| **窗口宽度** | 约 708 | 552 | 偏窄 |
| **左列 x** | 约 65（头像右侧） | `LegacyTextX=150` | 偏右 85px |
| **右列 x** | 约 281 | `LegacyTextColumn2X=305` | 接近 |
| **两列语义** | 左列在头像右侧偏下，右列在右上 | 左上 + 右侧 | **布局语义不同** |
| **第二组选项** | 出现在左列下方 | 无对应实现 | 缺失 |

### 6.4 用户口述补充

> 「整个的对话框的高度是可以自由地缩放的。就是内容如果长的话，它就会往下延伸。
> 所以它应该是分三个部分，第一个是顶部、中间部和底下这个部分。」

确认了 6.3 的「动态高度 / 三段式」：中段需按内容行数纵向拉伸，
这是当前固定 176 高度实现**无法表达**的。

### 6.5 修正方案（待实施）

1. **窗口改动态高度**：`Size.Y = 顶段 + 正文行数 * 行距 + 底段`，
   背景 F1100 按三段绘制（顶/底固定，中段纵向 repeat）
2. **左列 x 约 65**（避开 97 宽头像 + 间距），**右列 x 约 281**
3. 菜单条跟随所属列（右列菜单在右列，左列选项在左列）
4. 商品面板 F1000（可见 300x307）同样按三段拉伸

**当前状态**：本轮只完成测量与方案，代码未改（避免未经验证的改动）。
实施需先做「三段式背景拉伸」绘制能力，再逐项验证。
